Alerts are findings raised by detectors that re-check your data on a schedule. Three detectors ship, all on: tool error rates, cost spikes and cache hit drops. They read every session regardless of agent, so Claude Code and Codex work count together. At `/alerts`, or through the "All alerts" link on Overview.

<Screenshot name="alerts" alt="Alerts: one unseen warning about a tool's error rate, the detectors panel, and the last-30-days strip" />

## The list

The filter control offers `Unseen · 1`, `All · 1`, `Warning`, and `Critical`; the default is Unseen. **Mark all seen** is on the right and is disabled when nothing is unseen.

Each row shows a severity pill (INFO, WARNING or CRITICAL), the title, the message, the detector name in monospace, a `tool=Edit` chip when the alert is about a tool or a `project=argus` chip when it is about a project, the time, and either a **Mark seen** button or a muted "seen" pill. Unseen rows carry a coloured rail on the left, blue, amber or red by severity; seen rows are dimmed.

The empty state is a green **ALL CLEAR** pill with "nothing recorded", "nothing unseen", "nothing warning" or "nothing critical" depending on the filter.

## What marking seen means

You acknowledge alerts; you never delete them. An alert stays in the list until its condition clears, at which point the next detector run marks it resolved and it drops out of the page. If the same condition comes back later, or its severity changes (for example a warning escalating to critical), the alert is re-raised as unseen so you notice it again.

Marking seen is a write, so it is refused while the [daemon](/docs/daemon/) is running and the dashboard is read-only.

## Detectors

The panel on the right lists three, all on:

| Detector | Label | Watches |
| --- | --- | --- |
| `tool_error_rate_spike` | `on · 7d vs 28d` | Each tool's error rate |
| `cost_spike` | `on · 7d vs 28d/wk` | Each project's estimated cost |
| `cache_hit_drop` | `on · 7d vs 28d` | Each project's prompt-cache hit rate |

All three compare the **window**, the last 7 days, with the **baseline**, the 28 days before that. Project detectors include the work a session delegated to sub-agents.

<Callout>
The panel's sub-label says the detectors "run after each ingest". They actually run on a timer: once when Argus or the daemon starts, then every 10 minutes.
</Callout>

## The tool error-rate detector

For every tool it compares the window with the baseline. A tool is only considered when it has at least 20 calls in each period, which keeps rarely used tools from producing noise.

| Case | Result |
| --- | --- |
| Baseline had zero errors and the window rate is at least 5 percent | **Critical**, titled `Edit started failing this week (no prior errors)` |
| Window rate ÷ baseline rate is at least 2 | **Warning** |
| Window rate ÷ baseline rate is at least 5 | **Critical** |
| Anything else | No alert |

The title for the ratio cases reads `Edit error rate jumped to 4.7% this week (baseline 2.1%)` and the message `Last 7d: 4.7% over 427 calls. Prior 28d: 2.1% over 1262 calls.` The alert's metadata keeps the tool name, both rates, both call counts and the multiple.

Sub-agent tool calls count towards these rates, since each call is its own row.

## The cost spike detector

For every project it compares the window's estimated cost with the baseline's **weekly** average. The baseline only covers the time the project existed: a project that started 20 days ago is averaged over its 13 days of baseline, not 28. A project needs at least a week of history before the window (so a newer project is skipped), at least $5 of cost in the window, and at least $1 per week in the baseline.

| Case | Result |
| --- | --- |
| Window cost ÷ weekly baseline is at least 2 | **Warning** |
| Window cost ÷ weekly baseline is at least 5 | **Critical** |
| Anything else | No alert |

The title reads `argus cost 3.2x its weekly baseline ($41.80 this week)` and the message `Last 7d: $41.80 over 312 turns. Prior 28d: $13.06/week over 1,104 turns.`, with the prior period shortened for a younger project. The project is named by the last segment of its path; the full path is kept in the metadata.

Cost is an estimate from the price table, so for subscribers on a flat fee it is not money spent. It still tracks how much work the agent did, which is what a spike reports.

## The cache hit drop detector

For every project it compares the prompt-cache hit rate of the window and the baseline. The hit rate here is input-side: cache reads ÷ (cache reads + cache writes + fresh input). Output tokens are left out, so a week of writing more code does not look like a caching problem. A project is only considered when it has at least 50 turns in each period and a baseline hit rate of at least 50 percent.

| Case | Result |
| --- | --- |
| Hit rate fell by at least 15 percentage points | **Warning** |
| Hit rate fell by at least 30 percentage points | **Critical** |
| Anything else | No alert |

The drop is measured in percentage points, not as a ratio. The title reads `argus cache hit rate fell to 61% this week (baseline 88%)` and the message `Last 7d: 61.0% of input tokens served from cache over 420 turns. Prior 28d: 88.0% over 1,530 turns. That is 27.0 points of input re-sent uncached.`

## Last 30 days

A strip of dots on a time axis from `-30d` to `now`, one per alert, sized and coloured by severity. Below it, two counters: alerts raised and critical.

## The sidebar badge

The sidebar's Alerts badge shows the unseen count, refreshed every 10 seconds. The dashboard does not raise browser notifications.
